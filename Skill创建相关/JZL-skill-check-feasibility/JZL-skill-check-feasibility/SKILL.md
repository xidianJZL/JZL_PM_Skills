# Skill Check Feasibility

评估场景是否适合封装为 Skill 的诊断工具。

## 触发方式

当用户描述一个场景并询问是否适合封装为 Skill 时，立即介入。

主动询问：

> 我来帮你评估这个场景是否适合封装成 Skill。先问几个问题，确保判断准确。

如果用户输入已包含足够的4维度信息，进入判断阶段；如果不完整，主动追问。

## 输入：4个必含维度

用户的场景描述必须包含以下4个维度，缺一不可：

| # | 维度 | 具体含义 |
|---|---|---|
| 1 | **业务场景** | 该任务是日常什么工作？输入、输出、用途是什么？ |
| 2 | **现有问题（LLM原生缺陷）** | 如果不做 Skill，让模型自由执行，会出现哪些不稳定、遗漏、幻觉、不规范问题？ |
| 3 | **场景固定约束** | 该任务有哪些固定 SOP、必填字段、统一规范、必做检查、禁止行为、私有资料依赖、工具依赖、人工确认节点？ |
| 4 | **复用性** | 是否高频、长期、团队通用，需要统一标准化执行？ |

### 软预处理策略

- Skill 尝试将用户输入拆解成4维度结构化信息
- 拆得清楚 → 继续
- 拆不准 → 主动追问用户（不阻断流程）

### 漏给维度的处理

- **不直接开工**
- 用 AskQuestion 主动追问
- 用户答完再继续
- **不用模型默认推断代替用户判断**

## 工作流：4步走

> **每一步都要把相应内容写入对应的 workdir 文档**，保证流程可追溯、结论可复用。

### 步骤1：初始化

**职责**：在脚本当前路径下创建工作目录，并落盘初始化日志。

**动作**：
- 检测操作系统（mac / windows）
- 在脚本当前路径下创建 `skill-check-workdir/`
- 读取 `templates/01-init.md` 模板
- 填充并保存到 `skill-check-workdir/01-init.md`
- 写入内容必须包括：
  - 会话信息（会话 ID、初始化时间、操作系统、工作目录）
  - 脚本版本（Skill 版本、场景清单版本）
  - 工作目录结构说明
  - 流程状态表（4个步骤的完成状态）

**产出**：workdir 就绪，`01-init.md` 已落盘

---

### 步骤2：澄清

**职责**：主动询问用户，确保4个维度全部澄清，并落盘原始澄清记录。

**动作**：
- 向用户逐项确认4个维度（业务场景 / 现有问题 / 场景固定约束 / 复用性）
- 对每个维度做软预处理（尝试拆解，不阻断）
- 拆不准则用 AskQuestion 追问
- 读取 `templates/02-clarify.md` 模板
- 填充并保存到 `skill-check-workdir/02-clarify.md`
- 写入内容必须包括：
  - **每个维度**独立一节，含：定义、用户描述原文、澄清状态
  - 维度完整度汇总表（4个维度的"是否完整 / 追问轮次"）
  - 澄清完成时间戳

**产出**：`02-clarify.md` 已落盘，含完整4维度结构化信息

---

### 步骤3：判断

**职责**：读取23类清单，匹配用户场景，并落盘匹配过程记录。

**动作**：
- 读取 `references/skill-scenarios-unified.md`，获取23类场景清单
- 读取 `skill-check-workdir/02-clarify.md` 获取用户在步骤2澄清的4维度信息
- 将用户场景拆解为4维度
- 对照23类清单逐类匹配
- 读取 `templates/03-match.md` 模板
- 填充并保存到 `skill-check-workdir/03-match.md`
- 写入内容必须包括：
  - 用户场景摘要（场景关键词、场景概述）
  - **23类清单匹配结果表**（每类的"匹配度 / 匹配依据"逐项填写）
  - 高匹配场景分析（主要 / 次要 / 不匹配三档分类说明）
  - 5项判断信号评估表（流程可定义 / 失败可避免 / 重复可复用 / 代价不可逆 / 资产可沉淀）
  - 匹配完成时间戳

**产出**：`03-match.md` 已落盘，含完整的23类匹配过程 + 匹配结论（适合/不适合/部分适合 + 命中的场景类型）

---

### 步骤4：输出

**职责**：输出结构化评估结论，并落盘到两份文档（工作目录根目录的报告 + workdir 内副本）。

**动作**：
- 基于 `03-match.md` 的匹配结果生成最终结论
- 读取 `templates/04-final.md` 模板
- 填充两份：
  - **主报告**：保存到工作目录根目录，命名格式 `skill-check-YYYYMMDD-HHMM-{场景关键词}.md`（示例：`skill-check-20260714-1030-周报生成.md`）
  - **副本**：保存到 `skill-check-workdir/04-final.md`

**两份文档写入的必含3项内容**：

| # | 产出项 | 写入位置 |
|---|---|---|
| 1 | **是否适合做成 Skill** | 最终结论区（结论 + 置信度） |
| 2 | **属于哪种场景** | 匹配的典型场景类型表（Top 3 排名 + 匹配依据） |
| 3 | **判断的依据** | 4维度逐项分析节（每维度的"分析 + 与 Skill 封装的关联"） |

**附加写入**：
- 报告信息表（文件名 / 评估时间 / 场景关键词）
- 判断依据总结（支持因素 / 不支持因素）
- 建议章节
- 参考文档链接

**产出**：
- 主报告 `skill-check-YYYYMMDD-HHMM-{场景关键词}.md`（工作目录根目录）
- 副本 `04-final.md`（workdir 内）

## workdir 结构

```
<脚本当前路径>/skill-check-workdir/
├── 01-init.md          # 初始化日志
├── 02-clarify.md       # 4维度澄清原始记录
├── 03-match.md         # 23类清单匹配过程
├── 04-final.md         # 最终评估报告
└── cancelled.md         # 中断占位（如发生）
```

## 流程中断处理

**中断触发**：用户在任意步骤撤回。

**处理方式**：
- **全部保留** workdir 内容，方便用户回看
- 如发生中断，留 `cancelled.md` 占位
- 不清理任何中间文件

## 不提供的功能

- **不提供重跑入口**：一次评估结束就结束，想重测就重新跑一遍 skill

## 核心设计原则

1. **用户第一**：场景适不适合，用户说了算；skill 不替用户推断
2. **结构化澄清**：4维度是必含门槛，缺一不可追问
3. **透明可查**：全流程留档，用户随时可回看判断依据
4. **结论可复用**：报告本身是团队后续决策的参考文档
5. **轻量不侵入**：skill 跑完即走，不改变用户已有工作流

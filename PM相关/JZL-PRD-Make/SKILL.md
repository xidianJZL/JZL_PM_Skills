# JZL-PRD-Make

目标：把已相对清晰的产品描述分批写成可审阅、可迭代的 PRD 文档。

## 核心原则

- **增量写入**：每次只填充 `prd/PRD.md` 的一个指定模块，不重写前文。
- **用户确认后才能继续**：模块计划生成后、每个模块完成后、每次修改后，均须等待用户确认。
- **不编造**：`[待确认：...]` 标注不确定项。
- **自包含**：所有模板文件固化在 skill 目录 `templates/` 下，模板内容修改后脚本无需改动。

## 目录结构

```
JZL-PRD-Make/
├── SKILL.md                        # 本文件
├── scripts/
│   └── init_workspace.py           # 工作区初始化脚本
├── templates/
│   ├── PRD-L1.md                   # L1 模板（小配置/文案/规则）
│   ├── PRD-L2.md                   # L2 模板（单流程/单页面）
│   ├── PRD-L3.md                   # L3 模板（多角色/多页面）
│   └── PRD-L4.md                   # L4 模板（平台级/交易型）
└── reference/
    ├── prd-module-guide.md          # 模块计划写作指南
	├── _append-log.md				# 日志文件模板
	└── _module-plan.md				# 模块计划文件模板
```

## Step 0 — 确定复杂度等级

### 等级定义

| 级别 | 适用场景 | 对应模板 |
|---|---|---|
| L1 | 小配置、小文案、小规则调整 | `JZL-PRD-Make/templates/PRD-L1.md` |
| L2 | 单流程或单页面功能 | `JZL-PRD-Make/templates/PRD-L2.md` |
| L3 | 多角色、多页面、多状态 | `JZL-PRD-Make/templates/PRD-L3.md` |
| L4 | 平台级、交易型、复杂业务系统 | `JZL-PRD-Make/templates/PRD-L4.md` |

### 交互规则

- **用户已指定等级** → 直接采用，不询问。
- **用户未指定** → 主动输出上方表格，请用户选择并确认。只有用户明确回复后，才进入下一步。

---

## Step 1 — 确定输入源

按以下优先级确定 PRD 的输入来源：

| 优先级 | 来源 | 如何处理 |
|---|---|---|
| 最高 | 用户本轮提供的文字描述或文件路径 | 立即使用 |
| 次高 | `shaping/07-product-final-draft.md` | 读取文件内容 |
| 最低 | 已有 `prd/PRD.md` + `prd/_module-plan.md` | 进入**修改模式**（见 Step 4B） |

> 如果当前目录下不存在 `shaping/`、`prd/`、`prototype/` 目录，也不存在 `00-intake.md`，说明当前不在产品工作区内，需要进入 Step 2 初始化工作区。

---

## Step 2 — 判断/初始化工作区

### 判断逻辑

检查当前目录是否存在以下任一标记文件/目录，存在即视为已在工作区内：

- `shaping/`
- `prd/`
- `prototype/`
- `00-intake.md`

**已在工作区内** → 复用该工作区，不新建
### 初始化工作区

**不在工作区内** → 检查同级是否存在 `{name}-workspace/` 目录：

- **存在** → 复用该工作区，不新建。
- **不存在** → 在同级创建 `{name}-workspace/`。

### 运行初始化脚本

运行以下命令创建/补齐工作区结构：

```bash
python JZL-PRD-Make/scripts/init_workspace.py --name "<产品名>" --level "<L1|L2|L3|L4>"
```

**当且仅当**用户明确说明输入源为"用户描述/文件路径"时，额外传入 `--source` 参数（内容为用户提供的原始描述全文）：

```bash
python JZL-PRD-Make/scripts/init_workspace.py --name "<产品名>" --level "<L1|L2|L3|L4>" --source "<用户描述内容>"
```

脚本执行结果：

| 产物 | 条件 | 说明 |
|---|---|---|
| `inputs/source_note.md` | 仅当传入 `--source` 时创建 | 写入用户提供的原始描述/文件内容 |
| `prd/PRD.md` | 不存在时创建 | 根据等级写入对应模板（L1-L4） |
| `prd/_module-plan.md` | 不存在时创建 | 写入模块计划框架 |
| `prd/_append-log.md` | 不存在时创建 | 写入追加日志表头 |

---

## Step 3 — 完善并确认模块计划

### 读取模板指南

读取 `reference/prd-module-guide.md`，了解模块计划的具体写法规范。

### 填充模块计划

1. 根据 Step 1 确认的 PRD 复杂度等级，在 `prd/_module-plan.md` 中填入"本次选中模板"行。
2. 基于输入源内容和选中的 PRD 模板，规划合理的模块拆分，确保：
   - 模块粒度适中，逻辑连贯
   - 覆盖选中模板的所有章节
   - 强调：L2/L3/L4 的"核心功能模块详述"部分：每个功能模块（M1, M2…）均须包含目标、用户故事、流程、页面与交互、业务规则、验收标准（页面与交互包含页面、状态说明），具体格式见L2/L3/L4的模板

### 输出并等待确认

将 `prd/_module-plan.md` 完整内容输出给用户，请用户确认。若用户有修改意见，据实调整（以 PRD 模板为基础，不随意删减章节）。

**用户确认后** → 进入 Step 4（逐模块写入）。

---

## Step 4 — 逐模块写入 PRD（正常模式）

每次只写一个模块，写完即让用户确认，用户无异议后再写下一个。

### 循环流程

```
for 每个待完成的模块 in _module-plan.md 中的模块列表：
	1. 所有模块计划是否全部完成，如果全部完成，跳出循环；如果还有未完成的模块计划，按照顺序执行，进入下一步。
    2. 确认上一模块计划已确认完成或者当前模块是第一个模块计划（读取 _module-plan.md）
    3. 根据本模块计划 + 输入源 + PRD对应模块的模板，输出本模块内容的预览+待确认点给用户看
	4. 等待用户修改建议，如果有修改建议，根据用户反馈对模块内容预览进行修改，回到步骤3；如果用户明确确认本模块内容预览通过（例如用户回复：通过、确认、OK、继续等类似内容），进入下一步。
	5. 将本模块最终的内容追加写入 prd/PRD.md 对应章节，禁止重复追加相同的模块内容
    6. 读取 _append-log.md，按照模板内容，追加本模块计划的日志
	7. 读取 _module-plan.md，只更新模块计划中对应模块的状态，改为已完成；只修改状态，不允许修改其他内容。
    8. 继续下一循环
```

### 追加规则

- **追加位置**：严格写入 PRD.md 中本模块对应的章节，不得改动其他章节。
- **不重写前文**：已完成的内容一个字不动。
- **不确定项**：`[待确认：...]`，不捏造。
- **模块命名**：L2/L3/L4 的功能模块使用 `### M1 xxx模块` 的格式，后续模块递增编号（M2, M3…）。
- **业务规则编号**：R01 对应 M1，R02 对应 M2，以此类推。R01-1 对应 M1 模块的第一个子功能，以此类推。
- **功能清单编号**：M1-1 对应 M1 模块的第一个子功能，以此类推
### 模块确认后

追加记录到 `_append-log.md`：

```markdown
| YYYY-MM-DD | M1 xxx模块 | 输入源文件名 | 已确认 | [待确认项] |
```
### 结束
完成所有模块计划后，等待用户确认，用户确认后，完成PRD文档，更新`PRD.md`文件中的`修改记录`部分的内容。

## Step 4B — 修改已有 PRD（修改模式）

当用户要求修改已有且完成的 `prd/PRD.md`（局部修改，不重写）时执行。

### 进入条件

以下任一情况均视为修改模式：
- 工作区已存在，用户要求修改现有 PRD
- PRD 已完成全部内容，用户提出新的修改需求

### 修改流程

```
1. 用户提出修改要求，可能包含多个问题
2. 遵循规则：每次处理只改一个问题，一个问题就是一个独立的修改目标
3. 根据用户修改需求，定位到 PRD.md 的指定章节
4. 输出修改结果预览给用户看，让用户进行确认
5. 用户有补充意见 → 继续输出修改结果，回到步骤 4，直到用户确认当前问题修改完成（例如用户回复：通过、确认、OK、继续等类似内容）
6. 当前问题确认完成后，按照当前问题最终的修改方案写入 PRD.md 的指定章节 → 若存在待处理的下一个问题，回到步骤 2 继续处理；若无待处理问题，进入下一步；
7. 所有待处理的问题确认修复后，询问用户是否还有新的修改需求
	- 用户有新需求，回到步骤 2 循环执行全流程；
	- 用户无新需求，本轮修改结束
8. 更新 PRD.md 的`修改记录部分`用于保存本次文档修改的版本 + 更新 _append-log.md
```

### 修改规则

- **只改指定章节**：`prd/PRD.md` 的指定小节，不动其他部分。
- **只改两个文件**：本轮修改只涉及 `prd/PRD.md` 和 `prd/_append-log.md`，不对工作区其他文件做任何改动。
- **每次一个**：一次只处理一个问题，逐一确认，不批量处理多个问题。
- **修改记录**：一轮问题全部完成且用户确认完成后，在 `prd/PRD.md` 的"修改记录"表中追加一行；并在 `_append-log.md` 中追加本轮修改摘要，状态记为"已确认"。

## 停顿点（强制等待用户确认）

以下节点必须停下来等待用户确认，不得自动推进：

| 节点 | 等待内容 |
|---|---|
| Step 1 | 复杂度等级（用户未指定时） |
| Step 3 | 模块计划 `_module-plan.md` |
| Step 4 每次循环 | 每个模块完成后的内容摘要 |
| Step 4B 每次循环 | 每个问题的修改结果 |
| 修改模式结束 | 询问用户是否还有新的修改需求 |

## 输出要求

- **交付物**：`prd/PRD.md`
- **格式**：表格优先；流程/状态/ER 图使用 Mermaid；验收标准用 Given/When/Then
- **低复杂度裁剪**：L1/L2 不堆砌 L3/L4 的章节（不因模板有就写，空壳章节删除）
- **最终自检**：仅追加到 PRD.md 文末"附：自检与待完善清单"章节

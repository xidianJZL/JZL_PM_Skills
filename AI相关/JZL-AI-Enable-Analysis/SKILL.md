# AI-Enable Analysis

本 skill 覆盖从 **0 到 1 上线 AI 产品**的完整 8 步流程，每一步都有输入/输出、方法论、多轮对话清单和模板支撑。

**核心协议**：每一步（第 0~7 步）必须先输出预览 + 1~3 个待确认问题，用户答"确认"后才推进下一步。未确认不推进。

> 第 -1 步（初始化工作空间）为一次性、幂等的前置动作，使用前由你自己执行一次 `scripts/init_workspace.{ps1,sh}`，不需要走"预览+确认"的多轮协议。

## 第 -1 步：初始化工作空间

### 目的

在动手任何一步之前，先**就地**创建一个**可写工作空间** `ai_enable_workspace/`，并把 8 步的产出文件占位（基于 `references/template_00..07`）连同一份 README 索引一次性落盘，避免后续每步都要重新决定"东西写到哪"。

这是一次性、幂等的前置动作，**不会影响后续 0~7 步的任何行为**。

### 何时执行

- 第一次使用本 skill 时，**必须先执行一次**。
- 重跑会覆盖占位文件；如果你已经有自己的产出，请用 `git` 等自行备份后再跑。

### 使用方式

**PowerShell（Windows）**：

```powershell
# 在你想作为工作目录的文件夹下执行（在 Cursor 中 cd 到那里再跑）：
.\scripts\init_workspace.ps1

# 指定路径 + 强制覆盖：
.\scripts\init_workspace.ps1 -Path . -Force

# 仅预览将执行什么，不实际写入：
.\scripts\init_workspace.ps1 -DryRun
```

**Bash（macOS / Linux）**：

```bash
chmod +x ./scripts/init_workspace.sh     # 首次需要加执行权限
./scripts/init_workspace.sh

./scripts/init_workspace.sh --path . --force
./scripts/init_workspace.sh --dry-run
```

### 输入 / 输出

- **输入**：当前路径（或 `-Path / --path` 指定路径）。
- **输出**：在目标路径下创建：

```

├── README.md                       # 索引 + 重跑说明
├── 00_value_hypothesis.md          # ← 模板 00 拷贝（占位）
├── 01_scenario_clarification.md    # ← 模板 01 拷贝（占位）
├── 02_atom_breakdown.md            # ← 模板 02 拷贝（占位）
├── 03_ai_feasibility.md            # ← 模板 03 拷贝（占位）
├── 04_ipo_analysis.md              # ← 模板 04 拷贝（占位）
```

## 第 0 步：价值假设与成功标准

### 目的

在动手之前，先验证"为什么要做这个产品"，防止上线即失败。

### 输入/输出

- **输入**：用户的初始想法（可能很模糊）
- **输出**：价值假设文档

### 方法论

**一句话定位公式**：

```
我们为【谁】，在【什么场景】下，提供【什么价值】，区别于【谁/什么】。
```

**三个关键假设**（必须能被人挑战）：

| # | 假设 | 假设不成立影响（高/中/低） | 验证方式 | 验证成本 |
|---|---|---|---|---|
| 假设A | 用户真的有这个痛点 | 高 | 用户访谈 5 人 | 1 周 |
| 假设B | AI 能比现有方案好 5 倍以上 | 中 | 内部 PoC | 2 周 |
| 假设C | 用户愿意付费/留下 | 高 | 灰度 | 1 个月 |

**指标体系**：

- **北极星指标**：1 个，唯一，能反映核心价值
- **过程指标**：3 个，能在不同阶段诊断

**Out of Scope（明确不做）**：列出 v1 不做的事，避免 scope creep。

### 多轮对话

| 轮 | 主题 | 关键问题 |
|---|---|---|
| 1 | 一句话定位 | "请用一句话说清楚：谁，什么场景，什么价值" |
| 2 | 三大假设 | "你认为做这件事哪 3 件事必须为真？" |
| 3 | 北极星指标 | "用一个数字衡量成败，会是哪个？" |
| 4 | Out of Scope | "v1 你明确不做哪些？" |

### 输出

1. 根据 `references/template_00_value_hypothesis.md` 填充价值假设文档
2. 输出预览 + 1~3 个待确认问题
3. 用户确认后推进第 1 步

## 第 1 步：场景澄清

### 目的

把模糊的"想法"变成"具体可验证的场景"，明确 **谁 / 为何 / 何时 / 在哪 / 怎么做 / 成功标准**。

### 输入/输出

- **输入**：价值假设文档
- **输出**：场景澄清文档

### 方法论：4 层澄清

**第 1 层 5W2H（七变量）**：

| 维度 | 问题 | 例 |
|---|---|---|
| What | 一句话定义场景 | "把碎片产出聚合为可发周报" |
| Why | 痛点是什么 | "周五2小时拼凑，质量参差" |
| Who | 谁会用 | 一线员工 + 其上级 |
| When | 何时触发 | 每周五 16:00 |
| Where | 在哪发生 | SaaS Web + 企微小程序 |
| How | 主流程概述 | 抓数据→AI汇总→生成草稿→人审→发送 |
| How much | 量化目标 | 提交率≥80%，耗时<10分钟 |

**第 2 层 Persona 画像卡**：

```
- 名字/头像 + 年龄/职业/地点
- 典型一天（关键节点）
- 核心痛点（用"我每次……就得很麻烦地……"句式）
- 现方案/备选方案
- 期待方案
- 不愿付出的代价
- 触达渠道
```

共生用户 + 利益相关方单独列出。

**第 3 层 JTBD（Jobs to be Done）**：

- 功能性任务：在何时完成什么具体事
- 情感性任务：想感受什么
- 社会性任务：想让别人怎么看自己
- **三问**：情境? / 动机? / 阻碍?

**第 4 层 EARS（系统行为规约）**：

5 个标准模式 + 4 个 AI 特有模式：

**EARS 5 标准模式**：

| 前缀 | 模板 |
|---|---|
| Ubiquitous（主路径） | 系统应当…… |
| Event-driven（事件驱动型） | 当 <触发条件> 时，系统应当…… |
| State-driven（状态驱动型） | 当系统处于 <状态> 时，系统应当…… |
| Optional（可选） | 在 <功能> 中，系统应当…… |
| Unwanted（异常） | 若 <条件> 成立，则系统应当…… |

**AI 特有 4 模式（建议补充）**：

| 模式 | 用途 |
|---|---|
| Confidence-driven（置信度驱动） | 置信度门控：置信度 ≥ θ 才执行 |
| Fallback-driven（兜底驱动） | 兜底：失败时降级路径 |
| Audit-driven（审计驱动） | 审计：强制落库字段 |
| Human-in-loop（人工） | 高风险人审门槛 |

### 多轮对话

| 轮 | 主题 | 关键问题 |
|---|---|---|
| 1 | 场景定位 | 一句话定位 + 谁会用 + 解决什么痛点 |
| 2 | Persona | 锁定 1~2 个核心用户群体，细化画像 |
| 3 | JTBD | 功能性/情感性/社会性任务分别是什么 |
| 4 | 现状 | 现在他怎么解决？痛在哪？ |
| 5 | 成功标准 | 北极星 + 2~3 个过程指标 |
| 6 | 边界 | v1 不做哪些？ |
| 7 | 异常剧本 | 用户最不爽的翻车场景是什么？ |
| 8 | 翻译成 EARS | 把上面所有讨论转为结构化句子 |

### 输出

1. 根据 `references/template_01_scenario_clarification.md` 填充场景澄清文档
2. 输出预览 + 1~3 个待确认问题
3. 用户确认后推进第 2 步

## 第 2 步：场景原子化拆解

### 目的

把场景细化为**可独立验证、可指派、可观察**的最小执行单元。

### 输入/输出

- **输入**：场景澄清文档
- **输出**：原子化拆解报告

### 方法论：两层拆解

**Layer 1 子流程（Phase / 子任务）**：

| 原则 | 含义 |
|---|---|
| 单一参与者 | 不切换主用户/系统角色 |
| 单一系统模块 | 不跨多个后端服务 |
| 独立可交付 | 产出可独立验收 |
| 时间聚合 | 几分钟~几小时 |
| 失败回滚完整 | 回滚代价在子流程内 |

**Layer 2 原子任务（动词级别）**：

6 大原则：
- 一个动词一个节点
- 输入最少必要
- 输出最少可行
- 可观察
- 可验证
- **颗粒度自检（3秒原则）**：熟手执行不超过 3 秒思考

**自检：MECE + 闭环**：
- M（互斥）：两个节点不重叠
- E（穷尽）：主路径 / 异常 / 退出都有节点
- 闭环：第 N 个节点的输出能流回第 1 个节点输入

### 多轮对话

| 轮 | 主题 | 关键问题 |
|---|---|---|
| 1 | 子流程拆分 | 从场景澄清的核心剧本中提取主流程，再按阶段切，列出所有个子流程 |
| 2 | 每个子流程的原子拆解 | 逐个展开，1 动词 1 节点 |
| 3 | 颗粒度自检 | 是否有节点 >3 秒？是否需再拆？ |
| 4 | 异常流补全 | 主要失败点？回退路径？降级策略（不停服的简化方案）？ |
| 5 | Mermaid 主图 | 主路径图 + 子图分组版 |
| 6 | MECE 检查 | 是否漏节点？是否重叠？ |

### 输出

1. 根据 `references/template_02_atom_breakdown.md` 填充原子化拆解报告
2. 输出预览 + 1~3 个待确认问题
3. 用户确认后推进第 3 步

## 第 3 步：AI 赋能可行性分析

### 目的

判断每个原子任务 **是否值得 + 是否能** 用 AI 赋能。

### 输入/输出

- **输入**：原子化拆解报告
- **输出**：AI 赋能可行性报告

### 方法论：10 维度打分

**A 组：作业可 AI 性（沿用 6 维）**：

| 维度 | 1（人友好）→ 5（AI/程序友好） |
|---|---|
| 输入弹性 | 仅结构化 → 非结构化 |
| 规则可语言化 | 说不清楚 → 显式可描述 |
| 示例可得性 | 无示例 → 示例丰富 |
| 输出弹性 | 需精确 → 允许容错 |
| 容错空间 | 错误代价极大 → 错误代价小 |
| 重复度 | 低重复 → 高重复 |

**B 组：AI 项目可行性（新增 4 维）**：

| 维度 | 1（阻碍）→ 5（可行） |
|---|---|
| 幻觉/准确性风险 | 错误难检 → 可识别修复 |
| 推理成本/经济性 | ROI 不通 → 单次成本 < 产出 |
| 数据冷启动 | 零样本 → 已有正样本 |
| 合规/隐私/可审计 | 强合规敏感 → 可脱敏可解释 |

**总分判读**：

- A 高 B 低 → 技术可行，落地前先解决工程/合规
- A 低 B 高 → 落地可行，但 AI 非最优解
- 双高 → 典型 AI 优势场景
- 双低 → 暂不实施

**角色三件套**：

| 等级 | 触发条件 |
|---|---|
| 免审 | 高置信 + 低风险 + 低成本 |
| 抽检 | 中置信 / 中风险 |
| 必审 | 低置信 / 高风险 / 合规 |
| 复核（Audit-only） | 仅事后追溯 |
| 否决权（Veto） | 高风险决策，人一票否决 |

**角色矩阵（象限图）**：

- X 轴：规则可语言化（不易说 → 可说）
- Y 轴：任务弹性（低 → 高）
- 4 象限：人 / 程序 / AI+人 / AI+程序

> **分类依据**：以"主体（人 vs 程序）× 模式（纯执行 vs AI 增强）"两轴交叉，4 象限自然落出 4 种执行模式。

### 多轮对话

| 轮 | 主题 |
|---|---|
| 1 | 逐节点打分（A 组 6 维） |
| 2 | 逐节点打分（B 组 4 维） |
| 3 | 承担角色 + 交互模式 + 人审查点 |
| 4 | 整体判读 |
| 5 | 风险与前置依赖 |

### 输出

1. 根据 `references/template_03_ai_feasibility.md` 填充 AI 赋能可行性报告
2. 输出预览 + 1~3 个待确认问题
3. 用户确认后推进第 4 步

## 第 4 步：IPO 分析

### 目的

把每个节点（特别是 AI 节点）的**输入 / 处理 / 输出**细化到**契约级**，并产出全局数据流转图。

### 输入/输出

- **输入**：原子化拆解报告 + AI 赋能可行性报告
- **输出**：IPO 分析报告

### 方法论：I / P / O 三段式契约

**I. 输入契约**：

来源 / 协议层 / 形态 / 字段表 / 长度限制 / 缺失策略 / 注入防护 / 版本

> **协议层**（取值：REST / gRPC / MQ / SDK / DB / 其他）：决定延迟、可靠性、幂等要求与失败语义，必须显式指定。

**P. AI 处理契约（AI 节点专属）**：

模型 / Prompt 模板 / 上下文构建 / Tool Use / JSON Schema / 置信度阈值 / 后处理 / 失败模式 / 日志与审计 / 成本预算

> **节点类型先标**：每个 AI 节点必须先标注类型，3 类的字段侧重不同：

| 类型 | 典型场景 | 字段侧重 |
|---|---|---|
| **生成式** | 写文案 / 写代码 / 生成摘要 | Prompt 模板 / JSON Schema（结构约束）/ Tool Use / 后处理 / 失败模式（幻觉） |
| **判别式** | 分类 / 评分 / 意图识别 / 情感分析 | JSON Schema（标签枚举）/ 置信度阈值 θ / 失败模式（误判）/ 日志与审计（ground truth） |
| **抽取式** | 实体抽取 / 字段解析 / 关系抽取 | JSON Schema（字段必填）/ 后处理（解析容错）/ 注入防护 / 失败模式（漏抽） |

> **成本预算**（必填）：包含 3 项 —— ① 每次调用 token 成本；② 单次任务成本上限（兜底熔断阈值）；③ 月度预算上限（触发自动降级 / 告警）。

**O. 输出契约**：

形态 / 协议层 / 必填字段 / 校验 / 消费方 / 副作用 / 审计字段

**数据流转图（DFD）**：

- 图 A：分层 DFD（用户→网关→编排→模型→RAG→工具→校验→用户）
- 图 B：每个节点的 IPO 子图（I→P→O 三框）

### 多轮对话

| 轮 | 主题 |
|---|---|
| 1 | 总数据流转图 |
| 2 | 逐节点 I/O 契约 |
| 3 | AI 节点 P 段（Prompt/Function Schema） |
| 4 | 副作用与审计 |
| 5 | 节点间一致性检查 |

### 输出

1. 根据 `references/template_04_ipo_analysis.md` 填充 IPO 分析报告
2. 输出预览 + 1~3 个待确认问题
3. 用户确认后推进第 5 步

## 第 5 步：风险与边界

### 目的

列出**可能出错的所有事情**及其应对手段。

### 输入/输出

- **输入**：IPO 分析报告
- **输出**：风险与边界文档（独立产出，可被第 7 步引用）

### 方法论：FMEA 风格

```
| 失败模式 | 触发条件 | 影响 | 严重度 | 概率 | 风险等级 | 缓解 | 兜底 |
```

**7 类风险**：

1. **模型风险**（幻觉/偏见/越狱）
2. **数据风险**（隐私/版权/偏差/冷启动）
3. **工程风险**（限流/超时/耦合）
4. **合规风险**（审查/出境/行业）
5. **业务风险**（不买账/绕过/KPI 假象）
6. **UX 风险**（不确定性表达不清/人审设计差）
7. **组织风险**（培训/改流程/替代焦虑）

### 多轮对话

| 轮 | 主题 |
|---|---|
| 1 | 7 类风险逐类过一遍，每个类有哪些具体风险点？ |
| 2 | FMEA 填表（严重度 × 概率 = 风险等级） |
| 3 | 每条风险的缓解措施是什么？ |
| 4 | 红线（绝对不可做的事）有哪些？ |
| 5 | 降级兜底路径是否清晰？ |

### 输出

1. 根据 `references/template_05_risk_boundary.md` 填充风险与边界文档
2. 输出预览 + 1~3 个待确认问题
3. 用户确认后推进第 6 步

## 第 6 步：MVP 落地

### 目的

把方案切成**最小可行闭环**，用最快路径验证价值。

### 输入/输出

- **输入**：风险与边界文档 + IPO 分析报告
- **输出**：MVP 落地文档（独立产出，可被第 7 步引用）

### 方法论

**切片策略**：

- 垂直切片：完整端到端最小闭环
- 水平切片：一个用户的完整旅程
- **推荐组合**：垂直 × 1 条 + 水平 × 1 个用户

**MVP 范围**：

- 必有：可独立交付的最小闭环
- 必无：与闭环无关的所有功能

**灰度**：

- 维度：用户 / 流量 / 地域 / 场景
- 节奏：1% → 5% → 20% → 50% → 100%
- 每段至少 N 天

**DoD（验收）**：

- 模型：准确率 ≥ X
- 系统：可用率 ≥ Y，P95 ≤ Z ms
- 业务：采纳率 ≥ W
- 合规：审计全通过

**回滚触发**：

- 模型跌破 / 系统跌破 / 投诉飙升 / 一次红线触发

### 多轮对话

| 轮 | 主题 |
|---|---|
| 1 | 选哪条垂直切片 + 哪个用户群作为水平切片？ |
| 2 | MVP 必有/必无清单确认 |
| 3 | 灰度节奏：每阶段的准入/退出条件是什么？ |
| 4 | DoD 阈值：模型/系统/业务/合规四类指标各是多少？ |
| 5 | 回滚触发条件：每条红线阈值是否清晰？ |
| 6 | 数据回流：上线后看什么指标？ |

### 输出

1. 根据 `references/template_06_mvp.md` 填充 MVP 落地文档
2. 输出预览 + 1~3 个待确认问题
3. 用户确认后推进第 7 步

## 第 7 步：AI 赋能方案（PRD）

### 目的

在前 4 步的产出之上，融合第 5 步风险与边界 + 第 6 步 MVP 落地，组装成一份**可交付、可评审、可落地**的方案文档。

### 写作顺序（先度量后技术）

> **先写度量，再写技术**。顺序如下，不要倒序：
> 1. **§9 度量与监控**（4 套：模型 / 系统 / 业务 / 用户感知）—— 先定义"成功的标准"
> 2. **§7 风险与边界**（引用第 5 步独立产出）—— 再定义"失败的应对"
> 3. **§8 MVP 切片**（引用第 6 步独立产出）
> 4. **§1~§8 总体架构 / 技术选型 / UX / 流程** —— 最后才是"怎么实现"

### 标准结构（11 章）

1. 背景与价值（引用 §0）
2. 用户与场景（引用 §1）
3. 任务地图（引用 §2 + §3）
4. 系统架构（技术选型 + 数据架构）
5. 关键节点 IPO（引用 §4）
6. UX 设计（交互模式 + 不确定性表达）
7. 风险与边界（引用 §5）
8. MVP 切片（引用 §6）
9. 度量与监控（**先写**）
10. 上线计划
11. 附录（Prompt 库 + Function Schema + 评测集）

### 强制项（任何 AI 方案必含）

- **失败模式 + 降级 + 兜底 + 红线 + 应急**（引用第 5 步）
- **四套度量**：模型 / 系统 / 业务 / 用户感知（**先写**）
- **每节点 Prompt 模板附录**（必须可复用）
- **每个 AI 节点的 Function Schema**

### 多轮对话

| 轮 | 主题 |
|---|---|
| 1 | §9 度量：4 套指标逐套确认（模型/系统/业务/用户感知） |
| 2 | §7 风险锚点：FMEA 摘要 + 红线是否覆盖所有高风险点？ |
| 3 | §8 MVP 锚点：灰度节奏 + DoD 是否与 §9 度量对齐？ |
| 4 | §4 系统架构：LLM 选型是否满足 §9 模型度量目标？ |
| 5 | §11 附录：每个 AI 节点是否都有 Prompt + Schema？ |
| 6 | Go/No-Go 检查：最终交付检查清单过一遍 |

### 输出

1. 根据 `references/template_07_ai_solution.md` 填充 AI 赋能方案文档
2. 输出预览 + 1~3 个待确认问题
3. 用户确认后完成
